# 03. 시각화 (그림·다이어그램)

## 1. 원칙

- 그림은 만드는 방식에 따라 세 가지로 나누고, 우선순위는 **① 추출 > ② 실행 > ③ 작성**이다.
  정답이 코드에 있으면 LLM 이 그리지 않아야 그림과 코드가 어긋나지 않는다.
- **원본은 텍스트 파일로 git 에 두고**, 이미지(SVG/PNG)는 빌드할 때 만든다. 이미지를 직접 그리거나 손으로 고치지 않는다.
- 외부 이미지(인터넷 그림, 남의 스크린숏)는 저작권 문제로 쓰지 않는다.
- 그림은 **필요성이 검증된 경우에만** 만든다(5절).

## 2. 원본과 생성 방식

| 방식 | 언제 | 원본 | 원본을 만드는 주체 | 생성 도구 |
|---|---|---|---|---|
| **① 추출** | 코드·DB·폴더에 정답이 있는 그림 | 프로젝트 코드 자체 | 없음 | pyreverse, 스키마 조회, 트리 스크립트 → Mermaid |
| **② 실행** | 코드 실행 결과를 보여 주는 그림 | 예제 코드(`.py`) | `code_author`(LLM), 실행 검증 통과 후 | Python 실행(matplotlib, 실행 추적) |
| **③ 작성** | 코드에 없는 개념·흐름·설계 의도 | 그림 명세(`.json`) 또는 Mermaid(`.mmd`) | `figure_writer`(LLM) | 변환기(코드) → mermaid-cli |

### ① 추출

| 그림 | 원본 | 생성 방법 | 결과 |
|---|---|---|---|
| 클래스 구조 | `projects/todo/step05/*.py` | `pyreverse -o mmd` → 그림 명세의 포함 클래스 목록으로 필터링 | `.mmd` → SVG/PNG |
| 폴더 구조 | 실제 프로젝트 폴더 | 폴더를 읽어 텍스트 트리 생성(`.venv`, `__pycache__` 제외) | 텍스트 블록 |
| DB 구조(ERD) | SQLite DB | `sqlite_master` 조회 → Mermaid `erDiagram` | `.mmd` → SVG/PNG |
| 모듈 의존 | 프로젝트 코드 | pyreverse 패키지 그림 필터링 | `.mmd` → SVG/PNG |

- 프로젝트 단계가 바뀌면 다시 추출한다.
- Protocol 구현 관계는 추출되지 않는다(실험 E4). 그림 명세의 "추가할 관계"로 보충한다.

### ② 실행

| 그림 | 원본 | 생성 방법 | 결과 |
|---|---|---|---|
| 실행 결과 | `code/ch03/ex03_02.py` | 격리 실행 → 표준출력을 `.out` 으로 저장 | "실행 결과" 블록 (**기본값**) |
| 오류 예시 | 일부러 오류를 내는 예제 | 실행 → traceback 저장 | 텍스트 블록 |
| 그래프 | matplotlib 예제 | `MPLBACKEND=Agg` + 책 공통 설정(글꼴·크기·색·메타데이터 고정)을 주입해 실행, 저장된 그림 수집 | PNG/SVG |
| 실행 추적 표 | 짧은 예제 + 추적 표시 | `sys.settrace` 로 줄마다 변수 값 기록 → 마크다운 표(20단계 이하) | 표 |
| 터미널 세션 | 명령 목록 | 차례로 실행해 명령과 출력을 함께 저장 | 텍스트 블록 |
| GUI·웹 화면 | 앱 코드 | Playwright 화면 캡처 | PNG (4단계, 필요한 책만) |

- 그래프 예제 원본에는 책에 실릴 코드만 두고, 글꼴 같은 공통 설정은 실행기가 주입한다.
- 한글 글꼴을 지정하지 않으면 글자가 빠지고, SVG 는 메타데이터를 고정하지 않으면 매번 파일이 달라진다(실험 E3).
- 실행 추적은 예제 자체의 출력과 섞이지 않게 따로 받는다(실험 E5).

### ③ 작성

| 그림 | LLM 이 쓰는 원본 | 이유 |
|---|---|---|
| 순서도, 상태도, 개념 관계도 | **그림 명세 JSON**(노드·연결) → 변환기가 Mermaid 생성 | 문법이 단순해 구조화가 쉽고, 따옴표·예약어 문제를 변환기가 막음 |
| 시퀀스, 시스템 구조 | **Mermaid 직접 작성** → 렌더링 → 실패 시 오류를 주고 수정(최대 2회) | JSON 으로 표현하기 번거로움. 실험에서 1회 수정으로 4/4 성공 |
| 자료구조·메모리 (리스트 인덱스, 변수 참조) | **데이터 JSON** → 전용 Python 렌더러 | Mermaid 로는 어색함. 책 전체에서 같은 모양 유지 |

그림 명세 예시(순서도):

```json
{
  "id": "fig03_02",
  "type": "flowchart",
  "nodes": [
    {"label": "사용자 입력 받기 input()", "shape": "box"},
    {"label": "입력값이 숫자인가?", "shape": "decision"},
    {"label": "제곱(x**2) 출력", "shape": "box"}
  ],
  "edges": [
    {"from": 0, "to": 1, "label": ""},
    {"from": 1, "to": 2, "label": "예"},
    {"from": 1, "to": 0, "label": "아니오"}
  ]
}
```

변환기 규칙:

- 노드 id 는 `n1, n2…` 로 직접 붙인다. LLM 이 준 이름을 쓰지 않는다(예약어 `end` 문제, 실험 E2-b).
- 라벨은 항상 따옴표로 감싼다(괄호·특수문자).
- 노드 15개 초과, 없는 노드를 가리키는 연결은 변환 전에 오류로 걸러낸다.
- 변환기 자체를 단위 테스트로 검증한다.

## 4. 처리 과정

```
그림 명세 → 원본 생성 → 렌더링 → 기술 검증 → 내용 일치 검증 → 번호·캡션 → 출력 형식별 변환
```

1. 그림 명세(`.yaml`)를 읽고 방식에 맞는 생성기를 고른다.
2. 원본에서 중간 결과(Mermaid 원본, 실행 결과, 표)를 만든다.
3. 렌더링한다. Mermaid 는 여러 그림을 한 번에 렌더링하고 공통 테마를 적용한다.
4. 원본 + 테마 + 도구 버전 해시가 같으면 다시 렌더링하지 않는다(그림 하나 6~11초, 실험 E2).
5. 본문의 `<!-- figure: fig03_02 -->` 표시를 조립 단계에서 이미지, "그림 3-2" 번호, 캡션, 대체 텍스트로 바꾼다.

**기술 검증**

| 검사 | 방법 | 실패하면 |
|---|---|---|
| 문법 | 렌더링 성공 여부 | 오류를 LLM 에 주고 수정(최대 2회), 이후 사람에게 넘김 |
| 결정성 | 같은 원본으로 두 번 생성해 해시 비교 | 글꼴·메타데이터 설정 수정 |
| 가독성 | 노드 15개 이하, 라벨 20자 이하, 한글 글자 누락 경고 0건 | 그림 분할·단순화 |
| 참조 | 본문에 "그림 3-2" 언급, 번호 연속 | 조립 오류 |

**출력 형식별 변환**

| 출력 | 그림 형식 |
|---|---|
| HTML/웹 | SVG |
| docx | PNG 2배 해상도 (Word 의 SVG 지원이 버전마다 다름) |
| PDF | SVG 또는 PNG 300dpi |
| 종이 인쇄 | 흑백으로 바꿔도 구분되는지 확인 |

## 5. 그림 필요성과 내용 일치 검증

렌더링·가독성 같은 기술 검증만으로는 **그림이 왜 필요한지, 본문·코드와 맞는지**를 알 수 없다.
필요성은 그림을 만들기 전에, 내용 일치는 만든 뒤와 본문을 쓴 뒤에 검증한다.

```
① 제안(근거 필수) → ② 독립 검토 2회 → ③ 사람 승인 → [생성·기술 검증] → ④ 내용 일치 → ⑤ 집필 후 재검토 → ⑥ 변경 시 재검증
```

**① 제안 — `chapter_planner` 가 그림마다 필요성 명세 작성**

- 돕는 학습 목표(목표 번호)
- 본문·코드만으로 부족한 이유: 구조 / 관계 / 흐름·분기 / 시간에 따른 변화 / 메모리·공간 / 수치 비교
- 대체 수단 검토: 문장·표·코드만으로는 왜 부족한가
- **핵심 메시지(takeaway) 한 문장**: 독자가 그림에서 얻어야 할 것. 캡션·일치 검증의 기준
- 구성 요소 목록(노드·단계)

명세 항목이 빠진 제안은 코드가 자동으로 반려한다.

**② 독립 검토 — `figure_reviewer`**

- 제안 역할과 다른 프롬프트를 쓰는 별도 역할(자기 제안을 자기가 승인하지 않음)
- 한마디 판정 대신 **기준별 점수**(학습 목표 기여, 본문·코드로 대체 가능한가, 다른 그림과 겹치는가)
- **2회 독립 실행해 같으면 확정, 다르면 사람 판단 목록**으로 보낸다. 실험(E6)에서 핵심 그림 판정이 실행마다 달랐다.
- **빠진 그림 찾기**: 장 설계서의 개념마다 "어려운 점" 태그(흐름, 상태 변화 등)를 두고, 해당 개념에 그림이 없으면 누락 의심으로 표시

**③ 사람 승인** — 장 설계서 승인 때 그림 필요성 표(제안 근거, 두 판정, 불일치 강조)를 함께 보고 최종 결정한다.

**④ 내용 일치 — 그림 생성 후**

| 대조 | 방법 | 자동화 |
|---|---|---|
| 그림 ↔ 필요성 명세 | 구성 요소 반영, 캡션 = 핵심 메시지 | LLM |
| 그림 ↔ 코드 | 노드·화살표를 코드 줄에 대응시킨 표 → 대응 안 됨·불일치 0건이어야 통과(시작·끝 노드 예외). 그림의 클래스·함수 이름이 실제 코드에 있는지 검사 | 대응표 LLM, 이름 검사 코드 |
| 그림 ↔ 본문 | 라벨 용어가 본문·용어집 표기와 같은가, 설명 순서가 같은가 | 용어 코드, 순서 LLM |
| 추출·실행 그림 | 코드·실행 결과에서 만들었으므로 일치. 캡션의 수치만 데이터와 대조 | 코드 |

**⑤ 집필 후 재검토**

- 핵심 메시지가 본문에서 문장으로 설명되는가(그림만 덩그러니 있으면 안 됨)
- 본문이 그림 없이도 충분하면 "중복 — 제거 후보"
- 본문에 긴 구조·절차 설명이 있는데 그림이 없으면 "추가 후보"

**⑥ 변경 시 재검증** — 그림 명세에 의존 대상(절 본문, 코드 파일, 데이터)의 해시를 기록하고, 바뀌면 "오래됨"으로 표시해 ④부터 다시 검증한다.

## 6. 도구

| 도구 | 쓰는 곳 | 비고 |
|---|---|---|
| mermaid-cli + Chrome | ①③ 다이어그램 렌더링 | 버전 고정(`tools/package.json`). 이 PC 에서는 설치된 Chrome 사용 |
| Python 변환기·렌더러(직접 작성) | ③ JSON → Mermaid, 자료구조 그림 | 단위 테스트 |
| pyreverse (pylint) | ① 클래스·모듈 그림 | 책 빌드용 의존성 그룹 |
| matplotlib | ② 그래프, ③ 자료구조 그림 | 책 빌드용 의존성 그룹, 공개 한글 글꼴 포함 |
| `sys.settrace` | ② 실행 추적 | 표준 라이브러리 |

Graphviz·PlantUML(Java 필요)·pandoc 은 개발 PC 에 없고, 도구를 늘리지 않기 위해 쓰지 않는다(pandoc 은 4단계에서 결정).
